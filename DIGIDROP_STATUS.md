# DigiDrop — текущее состояние

Дата обновления: 2026-11-09

## Реализовано в исходном коде

- Светлая приглушённая рабочая тема, рассчитанная на слабое освещение.
- Главный экран, список точек, экран точки со всеми строками/накладными, экран отдельной строки.
- Группировка строк по магазину и адресу; несколько накладных одной точки отображаются вместе.
- CameraX + Google ML Kit для распознавания поддерживаемых линейных и 2D-кодов.
- Включение фонарика, запрос разрешения камеры.
- Поиск точного кода по загруженному рейсу.
- При совпадении кода с несколькими строками показываются все подходящие точки и суммы количеств по каждой точке.
- Обычный розничный EAN не считается уникальной физической коробкой и не увеличивает счётчик сканирований.
- Базовая обработка GS1: извлечение GTIN AI (01), распознавание наличия AI (00) SSCC / AI (21) serial как признаков уникального идентификатора.
- Импорт CSV/TSV и базовый XLSX-парсер первого листа (shared strings, inline strings, ячейки по координатам).
- Локальное сохранение импортированного рейса в SharedPreferences и восстановление при следующем запуске.
- Раздельные ключи прогресса для разных строк с одинаковым товарным штрихкодом.
- Экспорт CSV с UTF-8 BOM и экранированием полей.
- Открытие внешнего картографического приложения через geo: и резервный URL Яндекс Карт.
- Звонок через системный экран набора номера.
- Сброс локального прогресса и списка неизвестных кодов.

## Новая функция: маршрут по фотографии (добавлено в исходный код)\n\n- Экран «Маршрут по фото»: выбор снимка/фото из галереи, русский OCR на устройстве через Tesseract (языковая модель загружается при первом использовании и кешируется локально).\n- Редактирование распознанного текста и списка адресов до геокодирования.\n- Геокодирование через Android Geocoder; нераспознанные адреса выводятся отдельно, маршрут не строится молча по неполным данным.\n- Оптимизация дорожного порядка через OSRM Trip API; карта Leaflet/OpenStreetMap показывает точки и дорожную геометрию. Для OCR-модели, геокодирования, OSRM и картографических тайлов требуется интернет; ранее загруженная OCR-модель работает офлайн. Публичный OSRM не имеет гарантии доступности.\n- Точки можно применить в активный рейс; позиции создаются как маршрутные остановки без фиктивных штрихкодов.\n- Требуется проверить CI-сборку и тесты на commit с этой функцией. Реальное качество OCR/геокодирования зависит от качества фото и структуры листа.\n\n## Расширение приёмки документов (в работе, 2026-11-09)

В существующую загрузку накладных добавлена обработка следующих типов:
- PDF: извлечение текстового слоя и OCR для сканированных страниц.
- Изображения: OCR фотографий накладных; изображения можно выбирать вместе с другими документами.
- Excel: XLSX (все найденные листы), XLS и XLSM.
- CSV/TSV/TXT: разбор табличного текста, включая русские выгрузки Windows-1251.
- Word: DOCX (таблицы) и DOC (извлечение текста).
- RTF: базовое извлечение текста и табличных разделителей.
- OpenDocument: ODS и ODT.
- Структурированные данные: XML, JSON и HTML-таблицы.

Импорт остаётся внутри существующего экрана «Загрузить накладную». Каждый файл обрабатывается как источник данных общего пакетного импорта; файл не считается отдельной накладной автоматически. Ошибки отдельных документов показываются, остальные документы пакета продолжают обрабатываться. Строки без штрихкода можно включить в маршрут, если есть получатель/адрес и количество; такие строки нельзя автоматически найти сканированием штрихкода.

Unit-тесты для XLS, DOCX, RTF, ODS, ODT, XML, JSON, HTML, кодировок текста и строк без штрихкода проходят в GitHub Actions run #775 (commit `979b53e6cb2d6b4432eaefd36e165ff1c406c8c1`). Проверка на реальных формах поставщиков и физических QR/этикетках остаётся обязательной перед эксплуатацией.

## Ограничения, которые остаются

- XLSX: читаются найденные листы книги; сложные связанные таблицы, формулы без сохранённых вычисленных значений и нестандартные схемы поставщиков требуют проверки.
- PDF и фотографии обрабатываются OCR, но точность зависит от качества скана, ориентации, таблиц и шрифтов. Проверка на реальных документах поставщиков ещё не выполнена.
- Парсеры табличных документов ищут распознаваемые заголовки и поля получателя/адреса, товара и количества. Конкретные схемы реальных поставщиков пока неизвестны; строки без штрихкода допускаются, но не могут автоматически сопоставляться сканером.
- GS1 обработан ограниченно. Полная спецификация GS1, все разделители FNC1 и любые варианты AI не реализованы.
- Если на нескольких точках один и тот же GTIN товара и на коробках нет уникального SSCC/серийного кода, определить физическую коробку для конкретного магазина математически невозможно. Приложение показывает варианты, а не угадывает.
- Подсчёт отсканированных упаковок возможен только для кодов, которые действительно уникальны и присутствуют в данных рейса. Сканирование обычного товарного EAN служит поиском товара/назначений, а не учётом каждой коробки.
- Геокодирование адресов зависит от доступности сетевого сервиса. Офлайн-открытие карт возможно только если на устройстве установлено приложение, способное обработать geo: URI.
- Автоматическая дорожная оптимизация с пробками не реализована; координатная сортировка по прямой не является навигационным маршрутом.
- Нет проверки на реальных этикетках и конкретном Android-телефоне в текущем окружении.

## Подготовка к рабочему тесту

- Пакетный импорт объединяет выбранные файлы в один импорт активного маршрута. Отдельный дневной реестр поставщиков и выбор груза/машины перед активацией маршрута ещё не реализованы.
- Для проверки реального сопоставления нужны исходные накладные и QR/штрихкоды пользователя. Не подставлять выдуманные значения.
